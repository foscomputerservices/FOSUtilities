# Releasing FOSUtilities

The ritual, in order. One commit covers steps 1 and 2 (the stamp commit); the release-consistency test in `FOSMVVMBootstrapTests` fails CI when they disagree.

1. `CHANGELOG.md`: move the `[Unreleased]` content under a new `## [X.Y.Z] - YYYY-MM-DD` heading.
2. `Sources/FOSMVVMBootstrap/Release.swift`: set `Release.version` to `X.Y.Z`. Projects generated by `fosmvvm-bootstrap` pin this release — the scaffold's FOSUtilities dependency renders from this value, so the pin bump is this step, automatically.
3. Commit as `docs(CHANGELOG): stamp X.Y.Z release (YYYY-MM-DD)` and push `main`.
4. Tag: `git tag X.Y.Z && git push origin X.Y.Z` — promptly after step 3: every project scaffolded from the stamped release pins `X.Y.Z`, and a stamped-but-untagged version cannot resolve for anyone.
5. GitHub release: `gh release create X.Y.Z --title X.Y.Z --notes-file <file holding the CHANGELOG section>`.
6. Template edits are not gated on the tag. CI scaffolds and builds every skeleton against the checkout under test (`--fos-utilities-path`, `FOSUtilitiesSource.localCheckout`), so a template may use an API introduced in the same PR. Only customer scaffolds resolve the pin.
