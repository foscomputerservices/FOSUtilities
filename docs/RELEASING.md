# Releasing FOSUtilities

The ritual, in order. One commit covers steps 1 and 2 (the stamp commit); the release-consistency test in `FOSMVVMBootstrapTests` fails CI when they disagree.

1. `CHANGELOG.md`: move the `[Unreleased]` content under a new `## [X.Y.Z] - YYYY-MM-DD` heading.
2. `Sources/FOSMVVMBootstrap/Release.swift`: set `Release.version` to `X.Y.Z`. Projects generated by `fosmvvm-bootstrap` pin this release — the scaffold's `{{FOS_VERSION}}` renders from this value, so the pin bump is this step, automatically.
3. Commit as `docs(CHANGELOG): stamp X.Y.Z release (YYYY-MM-DD)` and push `main`.
4. Tag: `git tag X.Y.Z && git push origin X.Y.Z` — promptly after step 3: the skeleton matrix resolves the scaffold's pin from the network, and a stamped-but-untagged version cannot resolve.
5. GitHub release: `gh release create X.Y.Z --title X.Y.Z --notes-file <file holding the CHANGELOG section>`.
6. **Pin-gated template edits — only now.** A template edit that calls an API first shipped in `X.Y.Z` lands only after the tag exists, because the skeletons scaffold and build against the network-resolved pin — such an edit landing earlier fails CI against the previous release. Sweep the queue of edits waiting on this release (a scaffold helper retiring in favor of a new framework API is the standing example) and land them as a follow-up commit; the next skeleton run proves them against the fresh tag.
